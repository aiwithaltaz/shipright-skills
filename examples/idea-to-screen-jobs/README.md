# Teaching example: an idea becomes a bounded screen brief

**ShipRight 0.6. Fictional authored example, not an observed trial.**

## User request

> I want a tool for freelance designers to track unpaid invoices. Phase one is a manual list with amounts and due dates.
> No payments, reminders or uploads. Use my existing purple theme and 4px spacing. Draft a screen brief; do not build it.

## Product frame

The user and job are clear. Ask zero questions before drafting.
Outcome: the designer can see unpaid work and decide what to follow up.
Current alternative and demand evidence are Unknown. Do not invent a competitor claim or a differentiator.
The useful mechanism is one manual invoice list. Its commercial value is not established by this brief.

Only the requested list is in current scope. Payments, reminders and uploads stay out.
The brief does not define edit/delete rights or paid-status behavior. Those actions remain open if needed later.

## Screen brief

Job: inspect unpaid invoices and their due dates.
Reuse existing table/list components, theme and spacing. Do not invent hex codes, fonts, filters, dashboards or sample business metrics.
Show approved fields only. State whether data is real or a labeled requested test fixture.
Handle empty, populated and load-failure states only when the actual data source supports those states.
Use the existing app navigation for an exit; no redundant Home button is needed.
Specify narrow-screen ordering and long invoice names without adding mobile-only features.

A proposed row grouping or sort is labeled Proposed, not silently added to build scope.
A draft can proceed while these choices remain open. Handoff readiness depends on which commitments are required next.

## Later feedback

> Remove the All clients dropdown. Keep everything else. This is not the payments phase.

Acceptance: dropdown absent, no replacement chips or tabs, existing data/actions preserved, no payment button.
The request authorizes that correction. Do not repeat the product intake or require a full audit.

## Evidence

A screenshot can establish visible hierarchy and the absence of the dropdown in that view.
It cannot verify keyboard use, saving, permissions or unseen states. Those remain Not verified until exercised.
This example demonstrates intended scope discipline; it does not prove real model performance.
