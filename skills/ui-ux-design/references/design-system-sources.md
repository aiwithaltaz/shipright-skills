# Design-system sources

Load for system-source provenance or a comparison that changes a decision. Consult original guidance only as needed; do not browse every system for every screen.
These sources are reference guidance, not this product's research findings, brand authority or approved system choice.
Original summaries below were prepared from official pages or indexed official content accessed on 2026-10-12. Public-page access does not grant asset redistribution rights. Verify current version and license when using code/assets.

| Source | What to learn and what not to copy |
| --- | --- |
| [Atlassian foundations](https://atlassian.design/foundations/) | Coherent roles for spacing/grid, color, typography, icons, illustration, elevation, borders and radius. Do not import Atlassian identity or every component. |
| [Spectrum introduction](https://spectrum.adobe.com/getting-started/introduction), [attention hierarchy](https://spectrum.adobe.com/foundations) | Shared language, context/platform adaptation and emphasis across visual/content/motion decisions. Spectrum 2 was current in reviewed pages; do not silently combine old and new guidance. |
| [Fluent principles](https://fluent2.microsoft.design/design-principles) | Platform familiarity, focus, inclusion and coherent identity. Its Microsoft brand and reuse percentage are not universal project requirements. |
| [Apple HIG principles](https://developer.apple.com/design/human-interface-guidelines/design-principles/) | Purpose, agency, predictable feedback, platform fit, inclusive input and deliberate craft. Use Apple conventions when the actual platform calls for them, not as a web-app skin. |
| [Material typography](https://m3.material.io/styles/typography/applying-type) | Type decisions should account for platform, engineering, resizing, density and adaptive layouts. Material is a reference unless selected, not a default theme. |
| [Carbon contribution lifecycle](https://www.carbondesignsystem.com/getting-started/contributing/product-development-lifecycle), [enhancements](https://www.carbondesignsystem.com/getting-started/contributing/enhancing-components) | Reuse/gap rationale, proportional contribution, documentation and criteria tied to evidence. Do not impose IBM teams, committees, legal process or enterprise tooling on small projects. |
| [Component Gallery about](https://component.gallery/about/), [systems](https://component.gallery/design-systems/), [components](https://component.gallery/components/) | Compare terminology, purpose and guidance across real systems, then inspect the original source. ## Access and evidence limits

Atlassian, Spectrum, Fluent and Component Gallery supplied readable page content. Apple/Carbon summaries also used indexed official text after some direct paths failed. Material direct extraction required JavaScript; only the listed indexed official guidance informed its summary. Do not claim a full source or component-code audit.
Record an unavailable source as unavailable; do not fill it with a guessed quote or current-version claim. Preserve prior research/mapping source registers and access dates.
Keep source class, title/URL, version/date if known, access date, selected property, original summary and limitations. Do not copy complete source articles, paid books or screenshot collections.
Screenshots and component galleries inform visual comparison, not observed user behavior or conversion. Apply the project's approved identity and current task before selecting reference properties.
