# Design foundations

Load only for requested system foundations or a task-relevant foundation gap. Do not rewrite a system for a small correction.
Use the inspected project system first. A missing document is not a missing system.
Reuse sourced values; choose new values only under requested or delegated design authority. Never claim proposals are existing brand facts.
Keep one coherent direction tied to the user job and approved identity, not a bundle of unrelated reference styles.

## Define only relevant foundations

| Foundation | Record the decision and its purpose |
| --- | --- |
| Color | Background, surface, text, action and status roles; supported contrast and non-color cues. Preserve approved identity; observed low contrast is not approval. |
| Typography | Existing or authorized family, task-based text roles, readable weight/line height, long content and fallback. Do not guess an exact font from an image. |
| Spacing | Existing rhythm and grouping; within-group versus between-group space. Name reused roles consistently, without designing a new token hierarchy. |
| Layout | Existing containers, alignment, reading order, content priorities, wrapping/overflow and supported width changes. Keep DOM and visual order coherent. |
| Radius | Existing shape language by purpose; record a justified exception rather than randomly rounding every surface. |
| Elevation | Borders, layers or shadows that communicate grouping/overlap. Avoid decoration that competes with the primary task. |
| Icons | Primary family, style, optical alignment and known role/platform/brand exceptions. Preserve approved meanings, labels and accessible names. |
| Imagery | Whether imagery serves the task; type, subject, placement, source/permission and alternative text if used. No-use is valid; do not invent logos or assets. |
| Motion | Whether motion explains a change; existing/requested purpose, timing source, interruption and reduced-motion alternative. No-use is valid; no automatic shaders or 3D. |
| Density | Task/content-driven information density across supported devices. Preserve readable text, usable targets, focus clearance and meaningful grouping; compact does not mean smaller everything. |

For each relevant role, record source/version, observed value or authorized choice, reason, decision status and affected use. Use existing names; exact values may be chosen under explicit delegation and recorded as delegated choices. Missing facts stay Unknown. Do not force light/dark, brand or density modes into an unrelated task.
An established system may intentionally vary marketing, operator and platform surfaces. Preserve the approved relationship and document the scope, not unrelated visual languages.

## Coherence and access

Try representative real or labeled prototype content, not only short ideal labels. Check long/missing text, grouping, touch/keyboard and relevant narrow/wide composition.
Preserve isolated accessibility issues even if the rest of the system is consistent. A reuse decision is not an accessibility Pass.
Borrow selected reference properties only. Check hierarchy, legibility and actual task completion before decorative polish.
Using an accessible library does not certify the composed experience. Written foundations do not prove rendered fit or runtime behavior.

## Scope and output

Use existing tokens as implementation sources. Detailed token schemas, transforms and theme architecture belong to Phase 6; detailed component contracts belong to Phase 7.
Show a concise direction, relevant decisions/gaps and next action. Export only requested/needed documentation; do not require a new DESIGN.md for every screen.
Carry the same approved foundation decisions into screen specifications and builder prompts. Keep observations, proposals and runtime evidence distinct.
