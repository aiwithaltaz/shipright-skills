# Design-system governance

Load for requested naming, reuse, contribution, documentation or system maintenance. Skip governance for a small correction.
Use the project's actual workflow. Governance should fit the project size; do not invent a committee or require new tools.

## One usable source

Record the canonical system location/version, actual components, naming and approval source. Preserve an existing schema and unrelated keys.
Use one name for the same role. Reconcile stale aliases in affected documentation; do not assume a rename migrates code, data or every consumer.
Name a maintainer only when supplied or delegated; missing ownership stays Unknown. A solo project may need only a source file, change note and an agreed reviewer.
Shared operating rules own decision status and readiness. System documentation does not create new approval authority or gate statuses.

## Reuse before contribution

1. Identify the in-scope user need and actual existing component/pattern.
2. Reuse it when it fits. Extend within authorized scope when a real gap remains. A new item needs a reason why existing options cannot meet the need.
3. Record the proposed change, reuse/extension reason, affected consumers and known accessibility/identity risks.
4. Apply actual approval or delegation; keep unresolved choices separate. Already authorized corrections do not need another ceremony.
5. Update the canonical documentation and affected handoff, then check the changed artifact at the right evidence stage.

Document purpose, source, use/non-use guidance, supported contexts, change date and relevant exceptions. Describe required checks without claiming they ran.
Conditional token guidance owns token records and implementation mappings; component contracts remain Phase 7. Do not add Storybook, Figma libraries, registries, telemetry or contribution forms just to appear mature.

## Exceptions and change

A deliberate exception records scope, reason, source/authority, affected uses and a review trigger when useful. Preserve approved platform/brand or role-specific differences; new unrelated-system mixing needs a clear reason and authority.
For a breaking change, identify known dependents, planned migration and verification gaps. Unknown aliases, redirects, adapters or rollback support stay Unknown.
Keep superseded decisions and old evidence historical. Updating documentation does not migrate or validate an implementation.
Deprecate only when authorized, with the existing alternative and affected-use plan; do not delete a shared component merely because one screen changed.

## Keep it quiet

Maintain the useful records behind the scenes. Show the recommendation, material risk or owner decision and next step. No mandatory meetings, new documents or global audit for a focused change.
Use Pass/Fail/Not verified/Not applicable with stage-appropriate evidence. Consistency is not proof of usability or accessibility.
