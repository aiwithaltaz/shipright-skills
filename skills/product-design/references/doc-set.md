# Writing requested project documents

Use after the frame is supplied, approved or delegated. Write only the requested files.
Follow [output-folder.md](../../_shared/output-folder.md). A request to write the set authorizes that work.
Do not stop after each document unless the user requests staged review or a new unresolved choice blocks the next file.

| Order | File | Source |
| --- | --- | --- |
| First | PRODUCT.md and 01-prd.md | Outcome, mechanism, jobs, phase and decision log |
| Next | 02-technical-architecture.md | Known stack, data and constraints |
| Next | 03-security-and-access.md | Actual roles, actions and data boundaries |
| Next | 04-frontend-spec.md and DESIGN.md | ui-ux-design owns screens, states and sourced system values |
| Next | 05-feature-ticket-list.md | Approved jobs, screens, dependencies and acceptance checks |
| Only if requested | 06-pitch-one-pager.md | PRD and named evidence; no invented traction |

Read existing documents first. Update authorized sections; preserve unrelated content.
A current explicit correction can supersede an approved older section without another approval round.
Unknown facts need a source and owner, not a guessed framework, permission, metric or integration.
Keep Proposed decisions separate from build scope. No fixed risk quota; include material risks only.

## Reconcile before delivery

- PRODUCT.md is a short export of the PRD, not a competing source.
- Roles in access rules match the actors allowed on screens.
- Screen IDs match jobs and tickets. Tickets name affected states or explain non-applicability.
- Screen scope matches the current phase, including explicit exclusions.
- DESIGN.md and screen specifications reference the same sourced tokens and components.
- Exact feedback is reflected in acceptance checks. Later ideas remain notes.
- Export paths resolve inside the user's project. Do not leave pack-local skills/ links in copied documents.
- Completed sections have no template comments or fake facts. Unknowns remain explicit and may block readiness.

Launch tasks belong in a launch plan when relevant. Do not add a release audit to every minor feature ticket.
A one-page tool can have short architecture and access notes. Do not generate paperwork to appear thorough.
For a pitch, trace every claim to the PRD or named evidence. Keep it to one page.
A document can be complete as a draft while still containing decisions that prevent build readiness.
