# Findability

## Applicability

Load when approved content must be found through browsing, search or filtering. Skip tasks where these capabilities are excluded or irrelevant. Work from actual content, jobs, fields and system support; recommend a new capability only within authority and keep it Proposed. Do not add search, filters, saved searches, tags or analytics to complete a checklist.

## Specify the retrieval contract

Name the task, allowed corpus and actor/object scope. Specify only sourced searchable fields, match rules, available metadata and result destinations. Unknown matching, indexing, ranking, typo/synonym support, counts and scale stay Unknown. A chosen label or thesaurus does not prove backend capability. Distinguish known-item lookup from exploratory browsing; use the smallest justified approach.

For approved filters, record category/property, real values or date/range definitions, selection behavior and source. Define within-facet and across-facet combination rules only when sourced or authorized; otherwise mark them unresolved or Proposed. Do not silently choose OR/AND, default values, time zones or persistence. Sorting orders results; filtering changes the set. Keep these separate when applicable.

Use task-relevant labels and predictable values. Keep missing metadata and ambiguous names visible without inventing categories or merging records. Where alternative identifiers are already supported, explain disambiguation; a search match is not identity proof. Do not promise instant results, intelligent ranking or relevance without evidence.

## States, access and verification

Distinguish empty corpus, no matches, loading and failed retrieval. For no matches, preserve current approved criteria and permit supported editing/clearing of those criteria; clearing criteria is not deleting records. Preserve unrelated work and follow existing state/exit guidance. Announce meaningful result changes when implementation is specified; a map alone cannot verify assistive-technology behavior.

Apply access boundaries to results, previews, suggestions and counts, not only navigation. Protected records must not leak through facets or search metadata. Use roles-and-navigation guidance for actual capability boundaries. Do not put private queries, identifiers or tokens in URLs, analytics or logs merely to preserve search state. Keep unverified enforcement visible as a risk.

Check representative sourced lookup/browse tasks, partial/ambiguous inputs, zero results, restrictive combinations and relevant access/device contexts. Derive acceptance checks from the approved retrieval contract, not hypothetical filters. Unavailable runtime or participants means Not verified; plans and expert predictions are not findability validation. Keep isolated accessibility or safety issues visible under the synthesis contract. Return the recommendation and consequential uncertainties, not a methodology dump. Sources: IA2, IA4, A1 in ia-sources.md, directly linked from SKILL.md.
