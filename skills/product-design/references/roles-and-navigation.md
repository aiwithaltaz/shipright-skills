# Roles and navigation

## Applicability and source

Load when actual roles/capabilities affect destinations, content, search or direct entry. Preserve the existing access policy; this reference applies it to IA, not a new authorization framework. No default Owner/Admin/Member/Guest roles. Use actual actors and sourced capabilities; missing policy stays Unresolved. A relationship or role name alone grants no access.

## Map capabilities before menus

Record who can read or act on which object scope, source of that authority and denied behavior. Separate role, ownership, assignment and other actual constraints; do not assume all members see all records or that reading permits writing. Reuse the project's access matrix and shared decision statuses.

| Actual actor / constraints | Job / object scope | Allowed action / source | Existing destination / direct entry | Denied / recovery | Verification limit |
| --- | --- | --- | --- | --- | --- |

Expose destinations relevant to supported jobs, with consistent labels across role views where they name the same thing. Do not duplicate the product structure or invent role dashboards to fill a matrix. Keep visible navigation separate from underlying route/content structure; fewer visible items do not remove the other entry paths.

Hidden navigation is never access control. Require authorization on direct requests and object access, including bookmarked/deep routes and changed identifiers. Check actual permission scope on every relevant request; do not infer enforcement from a diagram, sign-in or a hidden control. Unknown enforcement is Not verified, not Pass. A known specified disclosure remains a failure at that stage even if a fix is planned.

Apply the same data boundary to search, previews, suggestions and facet/result counts. Do not disclose protected record names/existence through navigation or denial messages. Define a safe existing exit and preserved work without inventing support services. If access changes during a session, carry the unresolved behavior and verification need into the handoff rather than silently choosing a policy.

## Risks and handoff

Retain isolated accessibility and safety issues even without repeated patterns; reuse synthesis evidence kinds and tracing. A single reported leak can be an unresolved serious risk without being a confirmed breach. Keep the source, inspection limits and next check. Do not claim security/accessibility readiness from navigation success.

Builders receive only current approved capabilities, known route/object boundaries, denied behavior and acceptance/verification needs. Check allowed and denied actors, direct entry, object scope and metadata leakage when runtime access exists; otherwise report the limit. This reference authorizes no live permission change, recruitment, new auth provider or security certification. Show only concise role differences, risks and decisions.
