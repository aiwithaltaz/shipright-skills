# Opportunity research - reference (optional)

**Status: Public draft.** Used by `product-design` during **Frame product**.
**Pack:** ShipRight.

## When to run

- Only at **New product** depth, and only after the user agrees. Or when the user asks for it.
- Never for Quick fix or Focused improvement work.
- If the user declines, continue without it and do not ask again in the same session.

No paid tools, scraping, sign-ups or purchases without approval. If no browsing tool is available, ask the user for sources instead of guessing.

## Budget

Default: at most 5 alternatives and 10 sources, one pass. State the budget before starting.

## Output (one table + three lines)

| Alternative | What our user does with it today | Where it falls short for our user | Evidence (link, date checked) | Strength |
| --- | --- | --- | --- | --- |

**Strength:** Observed (you inspected it) · Reported (a source says so) · Inferred · Guess.

Then:

- **Possible opportunity (Proposed):** … tied to the approved or proposed outcome
- **Not shown by this research:** demand, willingness to pay, market size (unless sourced)
- **Scope effect:** none until the user approves a decision (log it as Proposed D#)

Include "doing nothing / a spreadsheet / email" as an alternative when that is what the user really does today.

## Rules

- A competitor missing a feature is not demand. A feature nobody has is not proof anyone wants it.
- Research never changes scope, metrics or positioning by itself; it only produces Proposed decisions.
- If the user asks to add a feature because a competitor lacks it, respect the user's decision and note once that the gap is not demand evidence.
- Describe competitors precisely. No "they only do X" without evidence.
- Keep the summary short; the table carries the detail.
